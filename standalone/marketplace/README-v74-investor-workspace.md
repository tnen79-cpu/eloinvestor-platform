# إلو مستثمر — v74

تكملة v73: أدوات عملية لاكتشاف الفرص وتحليلها ومتابعتها، مع إصلاح صلاحيات خاص ببيانات المستثمر.

## ما أضيف

- **مساحة متابعة مرتبطة بالحساب** في `workspace.html`: مشاريع محفوظة، مراحل قائمة مختصرة / مراجعة مستندات / تواصل / عرض / توقف، قائمة فحص من 8 بنود وملاحظات خاصة. البيانات تستخدم `investor_saved_projects.project_snapshot`؛ لا تُخزن الملاحظات في المتصفح. اختيار بنود المراجعة لا يمنح توثيقًا رسميًا.
- **أبحاث محفوظة**: حتى 5 أبحاث بالفلاتر الحالية، مع اسم، حذف، وعدّ النتائج الجديدة عند فتح الصفحة. تستخدم `users.investor_preferences.marketplace_searches`. لا توجد تنبيهات مجدولة أو رسائل تلقائية.
- **حاسبة السيناريوهات** في تفاصيل المشروع: سعر مفترض، ربح شهري مفترض وتكاليف إضافية، مع تغير الربح -20% / 0% / +20%، العائد السنوي على التكلفة الكاملة وفترة الاسترداد. الحسابات محاكاة؛ لا تغير بيانات الإعلان.
- **دليل صاحب المشروع**: حقول مساعدة لسبب البيع، مدة التشغيل، الإيرادات، الأصول، الالتزامات والتسليم، تُدمج في الوصف دون حذف النص الأصلي أو تكرار القسم. مؤشر اكتمال يوضح العناصر الناقصة، وليس تقييمًا ماليًا.
- **توصيات أوضح**: الملاءمة تقيس الميزانية والموقع والنوع والمجال التي اختارها المستخدم فقط. التوثيق لا يرفع نسبة الملاءمة تلقائيًا، والاختيارات غير المحددة لا تنتج نسبة مصطنعة.
- **الحفظ الصحيح**: إعادة حفظ المشروع لا تمسح ملاحظات المتابعة. فشل الحفظ أو تعارض تحديثين لا ينتج رسالة نجاح. تغيير الاهتمامات يحافظ على الأبحاث المحفوظة.
- ربط قسم المحفوظات القديم بمساحة المتابعة القائمة على بيانات الحساب.

## مهم قبل تشغيل الميزات الخاصة

فحص قراءة فعلي في هذه الجولة وجد أن جدول `users` يعيد بيانات `investor_preferences` للزائر المجهول. لم تُعرض محتوياتها أو تُنسخ إلى التسليم.

محاولة الوصول الإداري إلى مشروع Supabase `khzlqesyhkmucewiwmkg` رُفضت لعدم امتلاك الاتصال الحالي صلاحية على المشروع؛ لم أستطع تعديل الصلاحيات الفعلية أو تشغيل Advisors عليه.

الإصلاح الجاهز موجود في:

`supabase/migrations/20261011225215_investor_private_workspace.sql`

يجب تطبيقه بواسطة حساب يملك صلاحية المشروع، بعد توفر جداول وترقيات v16/v53 القديمة. يحتوي على:

- قيود RLS إضافية restrictive تمنع السياسات القديمة الواسعة من كشف الملفات الشخصية أو محفوظات مستثمر آخر.
- منع الحساب العادي من تعديل الدور والباقات والرصيد والتوثيق المعتمد.
- فصل صلاحية إدارة الفواتير عن صلاحية تغيير أدوار الحسابات.
- حصر استهلاك رصيد نشر المشاريع في صاحب الجلسة، ومنع تحديد حساب آخر.
- دالة `marketplace_security_ready` التي تتحقق منها الواجهة قبل قراءة أو حفظ الأبحاث والملاحظات الخاصة.

**النسخة الجديدة تمنع ميزات الحفظ الخاصة إلى أن تتوفر هذه الحماية.** لا يكفي رفع صفحات HTML لتفعيلها. هذا لا يصلح التسريب الموجود في القاعدة القديمة بحد ذاته؛ يلزم تطبيق SQL فعليًا.

الملاحظات مخصصة لحساب المستثمر، ولا يُمنح الأدمن أو مالك المشروع سياسة قراءة لها في الإصلاح الجديد. الوصول الخدمي الموثوق لقاعدة البيانات يظل من صلاحيات إدارة البنية التحتية.

## التحقق

نجحت 5 مجموعات اختبارات:

1. حسابات السوق والتصنيفات والفلاتر.
2. تفاعلات السوق والمقارنة والأخطاء.
3. السيناريوهات والملاءمة وتقييد المدخلات.
4. عزل بيانات الحساب في كود الوصول، الملاحظات والأبحاث، الحفاظ على البيانات، رفض الحفظ قبل حماية القاعدة، ودليل الوصف.
5. SQL على PostgreSQL محلي عبر PGlite: منع القراءة المجهولة وبيانات الحساب الآخر، حماية الدور والرصيد والتوثيق، صلاحيات الفواتير، واستهلاك الرصيد للحساب الصحيح. شمل الاختبار وجود سياسات قديمة واسعة وتطبيق الإصلاح مرتين.

نجح أيضًا فحص صياغة JavaScript والروابط الداخلية وJSON. اختبار PostgreSQL المحلي لا يعوض تطبيق الإصلاح وفحصه على Supabase الحقيقي، ولا يثبت كامل صلاحيات الأدوار القديمة. لم يتم اختبار المظهر على جهاز فعلي أو سيناريو التسجيل والمدفوعات والمحادثات كاملًا، ولم تُنشر النسخة.

```sh
npm ci
npm test
```

Node 20.19 أو أحدث مطلوب للاختبارات. ملفات الاختبارات وحزم التطوير ليست مطلوبة على استضافة HTML.

## ما يلزم قبل الإنتاج

- تطبيق الإصلاح بواسطة اتصال إداري يملك المشروع، ثم اختبار مستخدمين مختلفين وأدوار الإدارة وملفات التوثيق على القاعدة الحقيقية.
- اختبار الحسابات والمدفوعات والمحادثات والتوثيق والنشر من البداية للنهاية.
- فحص مرئي على الموبايل والديسكتوب.

هذه نسخة تطوير قابلة للمراجعة، وليست إعلانًا بأن المنصة جاهزة للإنتاج أو أن جميع وظائف المنافس تمت دراستها داخليًا.
